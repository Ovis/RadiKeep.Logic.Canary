# 前回DBを使った放送局・番組表同期の確認

実サービスのAPIを取得できても、既存データがある場合だけ局の無効化や番組更新に失敗することがある。
空のSQLite DBと前回の正常DBのコピーに同じ取得結果を反映し、保存結果を比較する。
本体の `StationLobLogic`、`ProgramScheduleLobLogic`、repository、migrationを使い、同期処理そのものはRunnerに複製しない。

## 実行の流れ

1. `canary-state` ブランチから `canary.db` と `manifest.json` を取得する。
2. 空の実行専用DBで局定義と番組表を同期する（`C020_INITIAL_DATABASE_SYNC`）。
3. 前回のDBを読み取り専用で開き、SQLiteのバックアップAPIで別の実行専用DBへコピーする。必要なmigrationはコピー側だけに適用する。
4. 同じ取得結果を本体の処理で前回DBのコピーへ反映し、期待する保存状態と比較する（`C021_INCREMENTAL_DATABASE_SYNC`）。
5. 検証済みDBから持ち運び可能なSQLiteスナップショットを作る。既存の取得・認証・録音チェックも実行する。
6. 全体がPASSで、mainからの実行の場合だけ `canary-state` に正常スナップショットを保存する。

局・番組表同期用のDBには資格情報を渡さず、HTTPホストや常駐ジョブも開始しない。
認証・録音用DBは従来の実行専用DBのまま使い、永続化しない。
状態DBのテーブルには本体と同じスキーマがあるが、保存を許可する行は局定義・番組表・EF migration履歴だけ。
設定・資格情報・録音予約・録音結果・通知などの行が入っていたら保存・復元を拒否する。本体の運用DBを入力に使わない。

## 実サービス応答の共有

新規同期のHTTP GETで受け取った成功応答をメモリに保持し、増分同期では同じURLの応答を再利用する。
両方で本体のAPI解析・変換・保存を実行するため、比較中の番組表変更をDB更新の不具合と誤判定しない。
取得失敗は成功応答として保存せず、本体の再試行処理に従う。増分側で新規取得になかったURLへの要求が発生したら失敗とする。
実行時CLIには実サービスを固定応答で置き換えるオプションを追加しない。

## 確認範囲と期待する状態

| 対象 | 範囲 | 確認内容 |
| --- | --- | --- |
| radiko局定義 | 全国局定義 | 追加・属性更新・消えた局の無効化・再登場時の有効化 |
| らじる局定義 | `config_web.xml` の全エリア・サービス | エリア属性・HLS URL・サービス追加削除・消えたエリアのサービス残存 |
| radiko番組表 | CLIで指定した1局の週間番組表 | 新規保存・既存IDの属性更新・重複なし・過去番組の保持と削除 |
| らじる番組表 | 指定エリア・サービスの今日と昨日（JST） | 本体の変換・更新・重複なし・過去番組の保持と削除 |

radiko番組表の全国取得は行わない。APIアダプターで指定局以外を取得対象から外す。
らじるの番組表も従来のCanaryと同じ指定局・今日と昨日に絞る。局定義の同期は全エリアを対象とする。

新規DBでは、radiko局定義・番組表の保存結果を保存前のAPI解析結果とも照合する。
らじる番組表は取得したID・タイトル・開始終了時刻と保存結果を照合する。新規・増分の比較では保存したその他の属性も比較する。
DB内部の採番、同期時刻、radikoの最終確認時刻は比較から除外する。

最新応答から番組が消えても、本体は過去の番組を直ちに削除しない。
前回DBの番組に最新取得分を上書きし、本体の「実行時刻の1か月前を放送日に変換した日付」より古いものを除いた状態を期待する。
削除処理が例外を内部で吸収しても、削除後のDBを照合するため残存を検出できる。
局の増減や番組変更そのものを障害とは扱わず、同期後の状態の不整合をFAILとする。

`C021_INCREMENTAL_DATABASE_SYNC_changes.json` に実際の行の追加・欠落・属性変更を、
`C021_INCREMENTAL_DATABASE_SYNC_mismatches.json` に期待状態との不整合を記録する。
属性変更はフィールド名を記録し、変更内容の本文や資格情報を出力しない。

### 既存の本体動作で検出できる例

現行の本体repositoryは、らじるの取得結果に含まれるエリアのサービスを置換する。
エリア全体が取得結果から消えると、そのエリアの既存サービスが残る。
固定応答の回帰テストではこの動作が `E-C021-MISMATCH` となることを確認する。
本PRでは本体のこの処理を変更せず、Canaryで不整合として検出する。

## 初回・破損・対象変更

- 初回：状態ブランチがない場合に限り、前回DBなしとして開始する。C021は実行したことにせず `SKIP` とし、C020と既存チェックがPASSなら基準DBを保存する。初回の全体PASSにはこのSKIPが含まれる。
- C020失敗：比較の基準が作れないためC021はSKIP。全体はFAILまたはWARNになり、状態ブランチは更新しない。
- 破損・取得失敗：初回として扱わない。チェックサム・SQLite整合性・外部キー・ファイル構成・保存対象外の行を検証し、復元失敗はFAILとする。
- migration：以前のスキーマはコピー側でmigrationする。現在の本体が認識しないmigrationを含むDBは拒否する。
- 対象変更：保存済みのradiko局・らじるエリア/サービスとCLI指定が異なる場合はFAILとする。別の対象への変更は明示的な状態リセットで行う。
- リセット：workflow_dispatchの `reset_state=true` で前回DBを使わず確認する。確認に失敗した場合は旧DBを維持し、全体PASSのときだけ置き換える。

## Orphan Branchの保存方式

`canary-state` のルートには以下の2ファイルだけを置く。

- `canary.db`：SQLiteバックアップAPIで書き出し、DELETE journalとVACUUMで単一ファイルにした状態DB。
- `manifest.json`：形式バージョン・確認対象・DBのSHA-256・取得時刻・本体とCanaryのコミット。

毎回親なしのコミットを作り、復元時のHEADを指定した `--force-with-lease` で更新する。
mainの履歴にはDBを入れず、状態ブランチから辿れる履歴も最新の1コミットに限定する。
通常の親ありコミットや想定外のファイルがあるブランチは上書きしない。
過去の到達不能Gitオブジェクトの物理削除時期はGitHubに依存するため、物理使用量が常に最新DB1個分になることまでは保証しない。

Canaryジョブに `contents: write` が必要になる。PR検証は `contents: read` のまま。
同一concurrency groupで実行の重複を防ぎ、さらにleaseで古い実行からの上書きを拒否する。
競合・権限不足・push失敗はジョブとstatusをFAILにし、前回の正常DBを維持する。
状態ブランチへの更新でCanaryを再実行するpushトリガーは追加しない。

状態DBはArtifactsへアップロードしない。従来のstatusと診断ログだけを3日保持する。
定期実行のPASSでは診断Artifactsを保存しないため、正常な変更一覧が必要なら手動実行で確認する。

## ローカルでの使い方

ローカルCLIは `state/input` と `state/output` を既定値にする。
入力と出力は別のディレクトリにし、認証・録音用のDBを渡さない。
同じ場所・親子関係・シンボリックリンク経由で重なる入出力は、前回DBに触れる前に拒否する。
初回は空の入力ディレクトリで実行し、全体PASSを確認したうえで出力の2ファイルを次回の入力へコピーする。

```powershell
dotnet run --project src/Canary.Runner/Canary.Runner.csproj --configuration Release -- --state-input-dir state/input --state-output-dir state/output
```

Gitからの受け渡しをローカルで試す場合は `scripts/canary_state.py restore`、全体PASS後に `scripts/canary_state.py publish` を使える。
publishは実際に状態ブランチを書き換える。CLI単体の実行ではGitへの保存は行わない。

## 回帰検証と限界

```powershell
dotnet test tests/Canary.Runner.Tests/Canary.Runner.Tests.csproj --configuration Release
python3 -m unittest discover -s tests/state_storage -v
```

実SQLite・本体のAPI解析と同期処理を固定HTTP応答で通し、局の増減・サービス削除・属性更新・番組更新・重複・保持と削除を検証する。
EF interceptorで保存漏れ・更新漏れを発生させ、Canaryが検出できることも検証する。
保存・復元・Orphan Branchの更新・競合拒否はローカルのbare Gitリポジトリで検証し、外部通信や資格情報は使わない。
最終的な実サービス確認は、既存のTailscale経路で手動実行し、初回の基準DB作成と次回の増分確認を行う。
実サービスで発生する全地域・全局・すべてのAPI変更を保証する仕組みではない。
